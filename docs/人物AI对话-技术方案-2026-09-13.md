## 1. 功能定位与已核实事实

> **本功能定位（林哥拍板，最高优先级，取代旧「档案应答体」）**：本功能不是一个"只答材料支持内容"的档案应答体，而是一个**由档案构建的人格体（derived persona）**——它**由档案构建、可以超越档案、允许即兴外推**，目标是让访客"和那个人说话"（沉浸式、自然、可像日常闲聊）。关键红线随之收窄并见 §14：①"不得编造"铁律**仅适用于 vault/正史/传记本身**（知识库既有素材与成书内容），人格对话属「创作性再现」，**允许外推、可说未被记录的话**；②人格对话输出**绝不回流** vault/正史（回流隔离）。

### 1.1 已核实事实（可直接引用）

【实测】三级可见性唯一来源 `server/privacy.mjs`：
- `isPrivateEntity(e)` / `isPrivatePath(p)`：私密层 `私人资料/`、`隐私/` → 未解锁时 **404**（不可枚举）。
- `isSecretEntity(e)` / `isSecretText(s)` / `isSecretPath(p)`：绝密人物（命中 `SECRET_NAME`）与内部施工稿（secret 类别）→ **403**。
- `mustHideEntity(e, unlocked)`（`privacy.mjs:66`）：未解锁时私密/非父母卷问卷实体从任何列表消失；绝密人物**以锁定档出现**（可见姓名，点开才 403）。
- `SECRET_COOKIE = 'mneme_s'`（`server.mjs:99`），`/api/secret/unlock` 设会话级 cookie（`server.mjs:350`），`isUnlocked(c)`（`server.mjs:103`），`locked(c)` 返回 403（`server.mjs:121`）。**绝密门与登录共用失败退避（5 次/分钟/IP）。**

【实测】`server/ai-draft.mjs` 已有兼容 OpenAI 的客户端：`hasLlm()`、`MNEME_AI_KEY/ BASE/ MODEL`（`ai-draft.mjs:44-50`），**已含反编造 system prompt**（`ai-draft.mjs:6-14`：材料不够标【待采】/【有界推演】）。`POST /api/ai/draft` 当前**恒返回 501**（`server.mjs:455`，语义"site does not write vault"）。

【实测】设备矩阵 `web/src/device.ts`：`detectOs()` 区分 harmony/ios/android/windows/mac（`device.ts:23-33`）；`detectShell()` 手机判定 `short<=520 || w<=720`（`device.ts:42`）；壳写入 `data-os/data-shell/data-pointer` 等，供 CSS 属性选择器分壳（非只靠 `@media`）。

【实测】UI 落点 `web/src/space/Graph.tsx:913` `<aside className="gp-sheet glass chrome">`；现有顺序：分组→姓名→提及/年份/别名→同篇共现→出现于→证据片段→`打开自档页 →` 按钮（`Graph.tsx:955-957`）。**新按钮插在 957 行之后、958 行 `</aside>` 之前。**

【实测】SQLite schema（`ingest/ingest.mjs:553-567`）：
- `documents(id, path UNIQUE, title, domain, doc_type, stage, volume, is_private, meta, body, raw_text, sha256, mtime)` —— **含 `raw_text` 与 `is_private`**。
- `entities(id, pinyin, std_id UNIQUE, display_name, aliases, relation_group, stage, role_doc_path, mention_count, first_year, last_year)`。
- `entity_mentions(entity_id, doc_id, hits)`；`wikilinks(from_doc, to_target, display_text, resolved, is_private)`；`evidence_spans(doc_id, kind, snippet)`；`timeline_events(doc_id, year, ...)`；`chapters(doc_path, secret, ...)`。
- 【实测】`部署手册 §6`：私密层 md **已扫入 `documents` 并标 `is_private=1`**，由 `/api/secret/unlock` 门禁保护；**但测试 P4 要求 `evidence_spans/entity_mentions/timeline_events` 不得挂在私密文档上**（`ingest/test-privacy.mjs:77-79`）——即私密正文在库，但其"提及/证据"链接被隔离。

【实测】部署：`0.25C / 0.5G`，`MinNum=1`（常驻、无冷启动），镜像当前 **316 MB**，`CSP default-src 'self'`（同源 SSE 可行），`MNEME_MODE=cloud` 只读收口。

## 2. Q1：部署形态可行性（量化评估 · 已纳入零费用硬约束）

> **【实测·关键前提】team-lead 已实查 CloudBase 环境 `the-memory-d1g13bjvuec88d3c4`**：
> 1. `DescribeEnvPostpayPackage` → `EnvPostpayPackageInfoList: []`、`EnvPostpayPackageNum: 0` —— **该环境没有 Token Credits 资源包**。按 CloudBase 官方 `ai-model-nodejs` 技能规定：无此资源包时 **AI 接口根本不可用**，须先购买。
> 2. `DescribeAIModels` → `cloudbase` 分组 `Models: []`（**未启用任何文本模型**）；`hunyuan-exp` 亦空；`hunyuan-v3` 仅 `hy3-preview`；`hunyuan-image` 分组是生图（文本对话用不上）。
> 3. 结论：**路线 C（CloudBase 托管 AI）当前不可用，且它本身是付费的**（Token Credits）；另一条 `MNEME_AI_*`（自带 key 的 OpenAI 兼容端点）也是**按 token 计费**。
> → **"手机端走云端 API" 与 "零额外费用" 在物理上不可能同时成立**，必须二选一（见 §11）。

### 2.1 路线 A：浏览器**全设备**本地推理（WebGPU / transformers.js / wllama / llama.cpp WASM）—— **零账单，现升为默认**

| 指标 | 0.5B Q4_0 | 1.5B Q4_0 | 3B Q4_0 |
| --- | --- | --- | --- |
| 权重下载体积（首屏/按需） | ~0.35–0.4 GB | **~0.9–1.1 GB** | ~1.8–2.0 GB |
| 浏览器端内存占用（WASM heap + KV） | ~0.5 GB | **~1.2–1.5 GB** | ~2.5–3.0 GB |
| 鸿蒙 ArkWeb | WebGPU **未开放**（仍 WebGL2） | 同上 | 同上 |
| 旧安卓 WebView | WebGPU 需 Chrome≥113；WASM SIMD 自 91 | 同上 | 同上 |
| CPU 回退速度（手机） | ~5–12 tok/s | **~2–6 tok/s** | <2 tok/s（不可用）|
| **中文第一人称角色扮演质量** | 极弱（见 §13）| 弱（见 §13）| 仍受限（见 §13）|

**关键风险（已核实）**：
- 【实测】HarmonyOS NEXT 的 ArkWeb **未正式开放 WebGPU**，现状为 WebGL2；第三方资料（`ufcn.cn 2026-02`）称 **WASM SIMD 也"尚未启用或受限"**。来源：华为开发者联盟论坛、ArkWeb 进程文档。→ 鸿蒙端本地推理只能走**纯 CPU 的 WASM 回退**，且 SIMD 可能不全速。
- 本项目 `device.ts` 专为鸿蒙/iOS/安卓做壳适配、`immersive.ts` 按 phone 壳降级 heavy-fx（林哥在意手机耗电与流畅）。在手机上**下载 0.4–1.1 GB 权重 + CPU 跑 1.5B（2–6 tok/s，300 token 回答需 50–150s）** 直接违背功耗与流畅度约束，且**本地小模型无法可靠遵循信源档的逐条引用/不编造约束（见 §13-B）**——但人格档本就允许外推，该约束仅作用于信源档与正史。
- 私密层门禁**必须在服务端**（不能靠前端遮罩），本地模型无法做"按 unlock 状态决定可见 chunk"——但门禁服务端化已就绪（§4），本地模型只负责生成、上下文由服务端组装，门禁不受影响。

**【判断】在"零费用"硬约束下，路线 A（全设备本地）是唯一零账单路径，故升为默认；但其体验与质量上限见 §13，须以降级设计兜底。若林哥接受"手机端云端 API"换取质量，则路线 C 可用但会产生账单（§11 路径 ③）。**

### 2.2 路线 B：CloudRun 自托管小模型（llama.cpp / node-llama-cpp）

| 规格需求 | 1.5B Q4 | 3B Q4 |
| --- | --- | --- |
| 常驻内存 | ~1.5–2 GB（模型 0.9GB + KV + 开销） | **~3.5–4.5 GB** |
| CPU | ≥1 核勉强；≥2 核顺 | ≥2 核 |
| 启动模型加载 | 5–15 s（一次性）| 10–25 s |
| 当前 0.25C/0.5G 是否够 | **不够**（内存差 3–4 倍）| **远不够** |
| 镜像体积影响 | 模型不应烤进镜像（否则 316MB→数 GB，部署变慢、违反镜像卫生）；需运行时从云存储挂载 | 同左，更重 |

**【判断】路线 B 需把容器规格升到 ≥1C/2GB（1.5B）或 ≥2C/4GB（3B），常驻成本约为现 0.25C 的 4–8 倍；且要自运维模型服务、并发、OOM。** 性价比低，且仍**按实例计费（非零）**。仅在"数据不出 CloudBase、强合规"诉求下考虑。

### 2.3 路线 C：云端 LLM API（CloudBase AI / `MNEME_AI_*`）—— **会产生账单，当前环境亦不可用**

【实测】CloudBase 提供 `@cloudbase/node-sdk` ≥3.16.0 的服务端 AI：`app.ai().createModel('deepseek'|'hunyuan-exp').streamText(...)` 返回 `AsyncIterable` 的 `textStream`，**但当前环境无 Token 资源包、未启用文本模型，接口不可用**；即便启用，**Token Credits 是付费的**。自带 key 的 `MNEME_AI_*`（OpenAI 兼容，见 `ai-draft.mjs`）同样**按 token 计费**。

| 指标 | 量级（估算） |
| --- | --- |
| 首 token 延迟 | 0.5–2 s（流式） |
| 单轮 token 成本 | **会产生账单**，见 §11 路径 ③ |
| 并发 | 服务端只做代理+I/O，0.25C 可支撑数十路 SSE（详见 §7）|
| 当前可用性 | **CloudBase 环境不可用（须先购资源包+启用模型）；`MNEME_AI_*` 须自备 key** |

**【判断】路线 C 质量最高、最易约束，但①当前环境不可用、②会产生账单，与"零费用"互斥。仅当林哥放开零费用、且为手机端（或全端）换取质量时启用。**

### 2.4 路线 D：全设备本地（零账单）—— **现即默认形态**

【判断】在零费用硬约束下，**全设备统一走本地模型**（桌面/平板优先 WebGPU，鸿蒙/iOS/安卓手机走 WASM CPU 回退，必要时手机用更小参数）。质量上限见 §13，以降级设计兜底。路线 C 仅在"放开零费用"时作为手机端或高质量档的补充。

### 2.5 "微调"这一层（关键判断）

- **语料体量换算（仅自档页）**：UTF-8 下中文约 3 字节/字。〈绝密人物〉 6.7 KB ≈ **~1.5k–2.5k token**；某公开层头部人物 20.6 KB ≈ **~4.5k–7.5k token**。注意：这是**自档页**体量，远小于上下文窗口；但**含支撑素材（聊天/朋友圈/问卷/证书/关系图谱）的全量语料见 §13-A**，可达 50K–90K token，可能超出本地小模型有效窗口。
- **微调的成本与复杂度**：284 人 × LoRA 适配器（rank 16–64），单适配器约 4–30 MB，合计 **~1–8 GB 适配器**；需 284 次训练任务、版本化、评估、动态加载/卸载的服务端。而"每人一份 JSON 语料包"仅 ~284×15KB ≈ **4 MB**，零训练、零服务复杂度。
- **技术本质**：微调教的是*风格/格式/分布*，不是可靠的*事实检索*。要把"〈绝密人物〉某日说过 X"可靠地"装进"模型，要么仍要 RAG/上下文，要么海量重复曝光——而本站每人数 KB，远不够。
- **【判断】不做微调。** 改用：**长上下文（全量人物语料入 prompt）+ 严格 grounding system prompt + 受控片段引用（chunk_id 引用 + 服务端回填）**。事实可控、可引用、可审计，且成本近乎为零。

## 3. Q2：语料构建管线

### 3.1 为什么不能直接用现有 ingest 产出

【实测】现有 `ingest/ingest.mjs` 产物是通用表（`entities/entity_mentions/evidence_spans/...`），目标是图谱/检索，**没有"按人物聚合的可对话语料包"概念**，也没有 `tier` 标注与引用锚点。直接复用会导致：(a) 每次对话现拼 SQL、易在门禁上出错；(b) 无法把"私密文档正文"与"公开提及"安全合并。故新增 `ingest/persona-build.mjs`，但**复用 ingest 已扫入的 `documents/entities` 等表作为输入源**（含 `is_private=1` 的私密正文）。

### 3.2 输入（复用现有表）

| 来源 | 用途 |
| --- | --- |
| `entities.role_doc_path` / `mention_count` / `aliases` / `first_year/last_year` | 自档页定位、门槛判定、人物元数据 |
| `documents.raw_text` + `is_private` + `path` | **语料正文**；私密正文已入库可直读（`部署手册 §6`）|
| `entity_mentions(entity_id, doc_id, hits)` | 公开层共现文档（按 hits 排序选 top-N）|
| `evidence_spans(doc_id, kind, snippet)` | 证据片段（公开文档才有，P4）|
| `wikilinks` | 同篇共现/关系 |
| `timeline_events(doc_id, year)` | 年份脉络 |
| `privacy.mjs` 的 `isPrivatePath/isSecretPath/isSecretEntity` | **chunk 级 tier 标注** |

> **缺口与处理**：私密文档的 `evidence_spans/entity_mentions` 被隔离（P4），所以"某公开人物也出现在私密文档中"时，管线**不能靠 mention 链接**找到私密正文，而要用 `documents.is_private=1` 中 `raw_text` 命中该人物 `display_name` 的方式补充私密 chunk（构建期做，服务端读取时仍受 unlock 门禁）。绝密 chunk 由 `isSecretPath/isSecretEntity` 标注。

### 3.3 输出结构与落点

**新增 SQLite 表（落在同一 `mneme.db`，随现有 ingest→deploy 同步，避免"db 未随镜像更新"历史故障）：**

```sql
CREATE TABLE persona_pack (
  entity_id   INTEGER PRIMARY KEY,
  display_name TEXT,
  mention_count INTEGER,
  has_role_doc INTEGER,
  support_assets INTEGER,            -- 是否有任一支撑素材
  tier_counts  TEXT,                 -- JSON: {public,private,secret}
  chunks       TEXT,                 -- JSON 数组（见下）
  built_at     TEXT
);
-- chunk 结构（每个元素）:
-- { id, tier:'public'|'private'|'secret', text, path, kind, year, evidence_kind }
```

**门槛判定（PM 结论 3）**，在 `persona_pack` 上预计算并存 `can_chat`：
```
can_chat = has_role_doc
           AND ( mention_count >= 20  OR  role_doc_size >= ~4KB  OR  support_assets >= 1 )
```

### 3.4 是否需要向量/RAG（结论已推翻：需要"检索注入"）

> **结论反转**：旧结论"不需要 RAG"建立在"全量语料几 KB–几十 KB 直接进上下文"的假设上。**新定位要求"必须包含档案中的所有内容"**，而头部人物的全量语料（自档页 + 支撑素材）实测可达 50K–90K token（见 §13-A），远超本地小模型有效窗口（~4–8K）。因此**必须引入"检索注入"（RAG-lite）**，且同步推翻 §0「向量/RAG」行旧结论。

【判断】**不需要 embedding 向量库，但需要"检索注入"**：
- **两层语料组织**：① **常驻人格基底** = 构建期生成的**压缩人格摘要**（`persona_spec` 扩为含"人生全貌"压缩段，≤3–4K token），始终在 prompt 内，保证人格一致性；② **按需检索注入** = 每轮按当前话题，用现有 **FTS5 trigram**（`store.mjs` 已具备）在 `persona_pack.chunks` 内检索 top-K 相关原始片段（带 `tier` 门禁），注入对话上下文。
- **不引入向量服务**：0.25C 容器不跑 embedding 模型；检索用 FTS5 关键词/trigram 即可（人物内语料体量小，关键词召回足够）。语义级"找相关人物"若未来需要，可在**构建期预计算**而非运行时。
- **效果**：单轮 prompt ≈ 人格摘要(3–4K) + 检索片段(top-K, ≤2–4K) ≈ 6–8K token，落在本地有效窗口内；而"档案中的所有内容"通过多轮检索 + 摘要覆盖，满足"完整性"要求（非单轮全装，而是会话过程中全覆盖）。

## 4. Q3：触达层门禁（最关键工程点）

### 4.1 三层强制，服务端唯一事实来源

- **chunk 级 `tier` 在服务端强制执行**：`persona_pack.chunks[].tier` 构建期由 `privacy.mjs` 标注；请求期再经 `isUnlocked(c)` 决定**哪些 chunk 进入 prompt**。前端遮罩仅作 UX，不作安全边界。
- **绝密人物（人物级整档锁）**：`isSecretEntity(entity)` 为真 → `GET/POST /api/persona/:id` 在**入口**即 403 `'locked'`（复用 `locked(c)`），需先 `POST /api/secret/unlock` 拿到 `mneme_s` 会话 cookie。复用现有绝密门，**不另建鉴权**。
- **普通人物（内容级逐条锁）**：入口开放；生成前按 unlock 状态组装上下文——未解锁只放 `tier=public` chunk，解锁后追加 `private/secret` chunk。**私密事实物理上不进未授权会话的 prompt。**

### 4.2 SSE 不断流的方案（先检索后生成 / 生成前定档）

【判断】采用 **"生成前定档"**：在调用 LLM 之前，服务端已根据该会话 unlock 状态确定**全部可入上下文的 chunk 集合**。LLM 只能看到被授权 chunk，因此"引用到私密片段"这种中途事件**不会发生**——不存在中途断流。伪代码：

```
function assembleContext(personaPack, unlocked):
  allowed = chunks.filter(c => c.tier === 'public'
                              || (unlocked && c.tier in ['private','secret']))
  return packChunks(allowed)            // 编号 [1]..[n]，附 path/kind/year

function chat(entityId, messages, unlocked):
  pack = db.persona_pack.get(entityId)
  if isSecretEntity(pack) and not unlocked: return 403 'locked'
  ctx = assembleContext(pack, unlocked)
  if not unlocked and questionHitsOnlyPrivate(pack, messages):
      return { needsUnlock: true }      // 前端弹解锁，不断流、不泄密
  stream = llm.stream(systemPrompt, ctx, messages)
  return SSE(stream, citations=resolveFromPack(pack))   // 引用服务端回填
```

### 4.3 "必须原文引用、禁止转述私密事实"的工程落地

- **提示约束**：system prompt 显式禁止"用自己的话重述私密事实"；要求任何 `private/secret` 事实**必须逐字引用 chunk 原文**并带 `[chunk_id]`。
- **受控引用集合**：模型只能从 `assembleContext` 给出的编号 chunk 中选引用；**无权编造 path**。
- **生成后引用校验（citation audit）**：
  1. 解析回答中的 `[chunk_id]` → 服务端在 `persona_pack.chunks` 中校验该 id 存在且 tier 被授权；
  2. 对 `private/secret` 断言，校验其是否被**原文片段包裹**（非自由文本改写）；
  3. 任一私密断言无有效 verbatim 引用 → 该段判为违规，返回【待采】兜底或整体拒答并重生成。
- **防伪造引用**：最终返回给前端的 `citations:[{chunkId, path, kind, year, snippet}]` 由**服务端用 chunk_id 回填真实 path/原文**，模型给出的"引用文字"仅作展示辅助、不被当作事实来源。

### 4.4 间接泄漏（【高】风险）兜底

即使模型看不到私密 chunk（未解锁），仍可能把**公开层**信息拼出私密推断。缓解：(a) 未解锁时 prompt 明确"你不知道该人物的私密/绝密信息，不得推测"；(b) 公开 chunk 本身已脱敏（`privacy.mjs` 的 `scrubMeta` 逻辑）；(c) 解锁后私密事实**强制原文引用**，使"改写泄漏"在 citation audit 阶段被拦截。

- 入参：`{ "messages": [{"role":"user","content":"..."}], "mode": "persona" }`（三档 **人格档 `persona` / voice / 信源档 `source`（原 `archive`）**；**默认 `persona`（第一人称、面向访客、允许外推）**；voice/信源 供不想沉浸者切换；档位定义见 §9/§10.3）。**〈绝密人物〉由绝密整档锁管辖**：未解锁访客不可对话；解锁（`<ADMIN_SECRET>` 管理员口令）后进入档案面板、对话按钮随之出现，可对话（含人格档）。
- 响应：`text/event-stream`（同源，CSP `connect-src 'self'` 允许）：
```
data: {"type":"chunk","text":"某同学A在"}
data: {"type":"chunk","text":"高中时期…"}
data: {"type":"citation","chunkId":7,"path":"高中/G2204/人物/同学/刘佑林.md","kind":"自述","year":2019}
data: {"type":"done"}
```
- 错误码：`403 locked` / `403 needs_unlock`（内容级，前端弹解锁）/ `401` / `429`（限流）/ `503`（上游 AI 不可用，回退本地脚手架或报错）。
- **供应商容灾**：主用 CloudBase AI `streamText`；失败时回退到 `ai-draft.mjs` 既有的 `MNEME_AI_*` OpenAI 兼容端点；再失败回退本地脚手架（仅做"无 AI 时"优雅降级，不编造）。

## 9. 三档口吻边界（林哥四条硬约束下的重定）

林哥四条硬约束：①人格档（`persona`，第一人称）升为默认、面向访客开放；②第一人称向访客开放（**〈绝密人物〉除外——她复用现有绝密整档锁，未解锁不开放、解锁后可对话，详见 §12.2**）；③对话向所有人开放（**〈绝密人物〉同上，不另设排除**）；④全设备兼容 + 零额外费用（已选零账单，路径 ③/④ 云端否决，见 §11）。据此重定三档：

| 档位 | 语义 | 默认值 | 是否允许外推/超越档案 | 面向谁 |
| --- | --- | --- | --- | --- |
| **人格档 `persona`**（第一人称） | "和那个人说话"：由档案构建的 AI 模仿体，**可即兴、可外推、可聊档案外的日常话题**；内容可能超出档案，绝非本人发言 | **默认档** | **是**（创作性再现）| 全体访客（沉浸式）|
| **voice 档** | 以该人物语域/称呼/口头禅作答，但**明示"档案再现、非本人发声"**，**不外推**（只陈述档案明确记录、未记录维度退化为"档案没写"）| 可切换 | **否**（仅语域仿真）| 想"像他说话"但不想被编造的访客 |
| **信源档 `source`（原 `archive`）** | 客观第三人称、逐条引用、严格不编造 | 可切换 | **否** | 想看档案依据的访客 |

**【判断·voice 档保留为中间档】**：不合并、不删除。理由——林哥要"和那个人说话"（人格档），也要"查档案"（信源档），中间应有"像他语气说、但不瞎编"的档位：① 让**无语域语料的人物**（B 级，见 §10.4）也能"像他说话"而不触发人格档的外推风险；② 给对"AI 编造"敏感的访客一个**既沉浸又克制**的选项。人格档与信源档的 system prompt **不可混用**（见附录 A）。

**默认值与门禁**：
- **默认 = 人格档**（第一人称、面向访客）；voice/信源 为可切换项，不切换即沉浸。
- **〈绝密人物〉 = 人物级整档锁（复用现有 `SecretGate`，不建 persona-policy 排除）**：未解锁访客不可见对话按钮、不可对话；输入 `<ADMIN_SECRET>`（管理员口令，`/api/secret/unlock`；**口令值仅存 CloudBase 控制台环境变量与 gitignore 的 `server/privacy.local.json`，本文档一律用占位符不写明文**）解锁后进入档案面板，**面板内对话按钮随之出现**，可选任意档位（含人格档）。

**合规处置（闸门从"仅 admin"打开，定位已重构，替代闸门见 §12）**：
1. **红线收窄（关键）**：旧"不得编造第一人称亲历记忆"一级禁忌**已作废**；新红线见 §14 = ①vault/正史/传记本身不得编造（仅约束信源档与未来成书）；②人格对话输出**绝不回流**正史（回流隔离，见 §12.2/§14）。人格档允许外推与即兴。
2. 显式披露（UI 常驻角标 + 首条消息声明 + 会话内可查说明，见 §12）；
3. 排除名单（可选库主 override，默认空；〈绝密人物〉不在此列，复用绝密整档锁，见 §12.2）；
4. 反向开关（第三方异议一键下线，见 §12）。

- 【判断】**默认档位 = 人格档（第一人称）**（林哥定位重构）；voice/信源 保留为可选项。人格档"模仿全维度特征"靠 `persona_spec` 的语域/用词/关注点仿真 + 由档案构建的人格基底；**但其外推/即兴不得冒充确凿事实、不得回流正史**——这是新定位下唯一成立的红线（见 §10.3、§12、§14）。

## 10. 人格规格（persona spec）设计与生成（回应林哥"为每个人物定制 AI、模仿各方面特征"）

### 10.1 特征维度清单（核心）

【判断】林哥要的"定制"正确实现 = **每人一份结构化 `persona_spec`**：声明该人物哪些特征维度被从语料抽取、如何驱动对话，而非"每人微调"。下表把维度做成一等公民；**voice 档**消费语域维度、**信源档（原 `archive`）**忽略语域维度只做引用、**人格档（原 `creative`）**额外允许第一人称与外推。

| # | 维度 | 从哪张表/字段抽取 | 抽取规则 | 如何进入 prompt | 如何防编造 |
| --- | --- | --- | --- | --- | --- |
| 1 | **语言特征**（语域、称呼方式、口头禅、句式习惯、错别字/标点） | 聊天记录时间线、朋友圈转录、问卷作答全文（**唯一能支撑"像他说话"的语料**）；其次自档页中第一人称段落 | 正则抽口头禅/标点习惯；wikilink/称呼表抽称谓；按 `doc_type` 区分载体 | 注入 `voice` 档 system prompt 的"语域约束"段（例："用短句、称林哥为'哥'、少用句号"） | 仅引用原文片段作为示例，**不得生成新表述**；无此类语料则该维度留空 → `voice` 退化为信源档 |
| 2 | **可核事实与时间线口径**（年份、学段、事件、地点） | `timeline_events(doc_id, year)`、`evidence_spans(doc_id, kind, snippet)`、自档页 `raw_text` | 按年份区间聚合；`evidence_kind` 区分自述/他述 | 作为 `persona_pack.chunks` 的事实基底（与 §3 复用） | 事实必须带 `[chunk_id]` 可追溯；无源不答 |
| 3 | **关系立场与称呼**（与林哥关系、称谓、亲疏的**可核表述**） | `wikilinks`、`entity_mentions`、`evidence_spans` 中显式表述 | 抽取"文中明确写出的关系/称谓"，**严禁用 `mention_count` 推人格或亲疏**（站内铁律，写进约束） | 注入"关系口径"段，限定可使用的称谓 | 禁止由提及次数反推"亲密/疏远"；只取显式记录 |
| 4 | **关注话题与价值观** | 自档页/聊天/问卷中**明确记录**的观点 | 仅取"文中直接陈述"的观点句，标注来源 chunk | 注入"关注点"段 | **不得由行为反推动机**；未明写的价值观标【待采】 |
| 5 | **行为习惯与典型场景** | `evidence_spans`、时间线事件中的可核行为 | 抽"某事件中实际做了什么" | 作为事实基底的一部分 | 只取可核事件，不泛化"他总是…" |
| 6 | **信息边界 / 回避项**（语料里**没有**的东西） | 构建期对以上维度做"缺失检测" | 若某维度无支撑语料 → 标记 `absent` | 注入"边界"段，驱动【待采】兜底 | **反编造的关键抓手**：明确告诉模型"此人物的 X 维度无记录，遇相关提问答【待采】" |

> 维度 1 的语料载体（聊天/朋友圈/问卷）按【实测】只覆盖极少数人 —— 这是 §10.4 覆盖度分级的根因。

### 10.2 生成机制（自动、批量、可复现）

**【判断】新建独立表 `persona_spec`，不扩列到 `persona_pack`。** 理由：`persona_pack.chunks` 是"能说什么"（事实语料，随语料更新），`persona_spec` 是"怎么说话/边界在哪"（特征抽取，规则变化才变）；两者更新频率与职责不同，耦合进同一表会相互污染、也违背"单一职责"。两者通过 `entity_id` 关联。

```sql
CREATE TABLE persona_spec (
  entity_id     INTEGER PRIMARY KEY,
  display_name  TEXT,
  lang_profile  TEXT,   -- JSON: { register, address_terms[], catchphrases[], sentence_habit, punct_habit, hasLangCorpus:bool }
  facts_profile TEXT,   -- JSON: 维度2/5 的摘要指针（引用 chunks，不复制正文）
  relations     TEXT,   -- JSON: [{target, stated_relation, source_chunk_id}]  -- 仅显式记录
  topics_values TEXT,   -- JSON: [{topic, stated_view, source_chunk_id}]
  backbone      TEXT,   -- 常驻人格基底：构建期生成的"人生全貌"压缩摘要（≤3–4K token），始终进 prompt 保人格一致性；见 §3.4/§13-A
  boundaries    TEXT,   -- JSON: { absent_dims:['lang'|'values'|...], notes }
  coverage      TEXT,   -- 'A'|'B'|'C'  -- 见 §10.4
  auto_generated INTEGER, -- 1=纯规则/统计；0=含人工确认维度
  confirmed_by  TEXT,   -- 人工确认者（林哥），NULL=未确认
  built_at      TEXT
);
```

**各维度能否自动抽？——硬规则：**

| 维度 | 自动抽？ | 规则 |
| --- | --- | --- |
| 1 语言特征 | **部分自动 + 需人工确认** | 正则/统计可抽口头禅、标点；但"语域是否可用作 `voice`"需林哥确认 `confirmed_by` 后才能启用（避免对未成年人/不熟者误仿真）|
| 2/5 事实与时间线 | **可自动**（规则+统计） | 直接聚 `timeline_events`/`evidence_spans`，零编造风险 |
| 3 关系立场 | **可自动抽显式表述**，但**禁止推演** | 只取文中明确写出的关系/称谓；`mention_count` 绝不入 spec |
| 4 价值观 | **可自动抽显式观点**，禁止反推 | 仅取直接陈述句 |
| 6 边界 | **可自动**（缺失检测） | 维度无支撑语料 → `absent`，驱动【待采】 |

**抽取阶段防编造硬规则（无论规则抽还是 LLM 抽）：**
1. 抽取器**只允许"引用原文片段 + 归因到 chunk_id"**，**不允许生成任何新表述**（尤其维度 1 的口头禅、维度 4 的观点，必须是原文片段，不得改写）；
2. 若用 LLM 辅助抽取（仅限维度 1/4 的归纳），prompt 强制"每条输出必须附 `source_chunk_id`，无源不出"；抽取结果经服务端校验 chunk_id 存在后才落库；
3. 任一维度无法用原文支撑 → 标记 `absent`，**不填空泛描述**。

**spec 与 chunks 的关系**：`persona_pack.chunks` = 事实语料（"能说什么"，带 tier 门禁）；`persona_spec` = 表达约束与边界（"怎么说话、哪里该【待采】"）+ 常驻人格基底（压缩"人生全貌"摘要，≤3–4K token）。对话时：先按 §4 取授权 chunks 作事实基底，再按 `mode`（信源档/voice/人格档）叠加 `persona_spec` 的语域/边界段与人格基底。两者解耦、各管各的。

### 10.3 三档边界（与 §9 表对应，林哥已裁决）

【判断】新定位下三档的**核心差异 = 是否允许外推**：
- **人格档 `persona`（默认）**：允许外推与即兴；内容可能超出档案。它消费 `persona_spec` 全维度（语域/称呼/关注点仿真）+ 常驻人格基底（压缩摘要）；**唯一约束（见 §14）= 不冒充确凿事实、不回流正史**。不再有"未记录事件一律【待采】"的强制（那是信源档的约束）。
- **voice 档**：只仿真语域/称呼，不外推；未记录维度退化为"档案没写"，不编造。
- **信源档 `source`（原 `archive`）**：严格不编造，逐条引用，未记录标【待采】——这条旧红线**只在信源档与未来成书（vault/正史）保留**。
- **门禁（§4 不变）**：三档都受 `tier` 过滤 + 原始引用约束（信源档强制逐字引用）；〈绝密人物〉由绝密整档锁管辖。
- 人格档 + 全维度仿真能否"像在日常生活里谈话"，取决于 §13-B 的本地模型人格质量与 §12 的披露/回流隔离。

### 10.4 覆盖度分级（新定位下重算，诚实结论）

【实测】284 实体中 ≥20 提及仅 41 人、≥50 仅 7 人、≥100 仅 1 人；且语言特征类语料（聊天/朋友圈/问卷）只覆盖极少数人。新定位下覆盖度**不再决定"能否编造"（外推已允许），而决定"像不像、全不全"**；重算三级：

| 级 | 判定阈值 | 新定位下的处理 |
| --- | --- | --- |
| **A** | 自档页充足 **且** 有语言特征语料（`hasLangCorpus=true`） | 人格档全维度仿真（语域/称呼/关注点可仿真）；质量最佳，最接近"和那个人说话" |
| **B** | 达 `can_chat` 门槛但**无**语言特征语料 | 人格档仍可用，但语域维度缺失 → 退化为"以第一人称叙述、但无口癖/称呼仿真"；可切 voice/信源 档补全依据 |
| **C** | 未达 `can_chat` 门槛（提及<20 且无自档页/支撑素材）| **仍给入口**（林哥"每个人物"诉求），靠外推补足；**强制"AI 模仿体·可能超出档案"披露**，UI 明示"该人物可用素材极少，回答多为推演" |

**【判断·明确结论】**：
1. **"为 284 人同等定制"仍不可行**——A/B/C 三级质量天差地别，C 级本质是"外推壳"，不是定制；但**外推已被允许**，故 C 级不再是"违规"，而是"低质量 + 须披露"。
2. **门槛语义变化**：旧"门槛 = 防编造"已废；新门槛 = **防"无料可仿却冒充"**——C 级可开放，但必须强制披露 + 不外推冒充确凿事实（见 §12/§14）。
3. **语言特征语料只覆盖极少数人** → 人格档在 B/C 级**退化为"第一人称叙述框架 + 无语域仿真"**；要"像他说话"，必须有聊天/问卷/朋友圈语料（维度 1）。
4. A 级才是真正"模仿全维度特征"；林哥的诉求在 A 级成立，在 B/C 级只能部分成立（但合法，因外推允许）。
5. **〈绝密人物〉不适用本覆盖度分级的"人人开放"**：她由 `isSecretEntity` 绝密整档锁管辖，未解锁访客不可对话，与覆盖度 A/B/C 无关；解锁（`<ADMIN_SECRET>` 管理员口令）后可在档案面板内对话。覆盖度分级只决定**非绝密**人物的口吻开放程度。

### 10.5 UI 形态（回应"按钮或其他形式"）

- **形态**：面板里是**一个入口按钮**（「与资料对话 →」），点进对话页后在**对话页内选口吻档位**（人格档/voice/信源档，按覆盖度开放；人格档为默认）。不把多档并列堆在 `gp-sheet` 面板上（空白有限）。
- **门槛不达标（C 级）**：仍给入口，但按钮/首条固定附「AI 模仿体·可能超出档案」披露，无"确凿依据"承诺。
- **有入口但无语言特征语料（B 级）**：进入后 voice/信源 档可用补全依据，人格档退化为"第一人称叙述、无语域仿真"。
- **绝密人物（〈绝密人物〉等）**：未解锁时面板按钮锁标、无对话；走现有绝密弹窗（`/api/secret/unlock`，输入 `<ADMIN_SECRET>`）解锁后，**面板内对话按钮随之出现**，可进入对话（含人格档）。不另建 persona-policy 排除。
- 档位切换需即时重渲染 system prompt（不改 chunks 事实基底）；档位选择记入本地会话（不上服务端，见 §4/§5）。

> §6 已同步本决策；前端改动文件同 §8（P0/P1/P2 的 `PersonaChat.tsx` 与 `Graph.tsx` 按钮位）。

## 11. 零额外费用约束下的全设备形态（林哥约束 ④ 的核心矛盾）

### 11.1 矛盾陈述（必须先正视）
林哥要求"电脑/平板本地模型 + 手机云端 API + 全设备兼容 + 零额外费用"。【实测】手机端云端 API 必然**产生账单**（CloudBase 当前环境无 Token 资源包、未启用文本模型，本身付费；`MNEME_AI_*` 亦按 token 计费）。**"手机端云端 API" 与 "零额外费用" 物理上不可能同时成立。** 下面穷举可行路径并量化。

### 11.2 四条路径量化比较

| 路径 | 形态 | 是否零账单 | 首字延迟 / 300 字回答等待 | 体验 |
| --- | --- | --- | --- | --- |
| ① 全设备本地（手机也 WASM CPU 回退） | 桌面/平板 WebGPU/WASM；手机 WASM CPU | **是（零）** | 桌面 ~0.5–2s / 数秒；手机 ~5–10s 首字 / **150–600s**（2–6 tok/s）| 桌面可用、手机极慢 |
| ② 桌面/平板本地 + 手机更小本地模型（0.5B Q4） | 手机降到 0.5B | **是（零）** | 手机 ~3–8s 首字 / **60–150s**（5–12 tok/s）| 手机仍慢但勉强 |
| ③ 桌面/平板本地 + 手机云端 API | 手机走 CloudBase/`MNEME_AI_*` | **已被否决——会产生账单（林哥选零账单）** | — | 否决（N/A）|
| ④ 购 Token Credits / 免费额度第三方 | 全云端 | **已被否决——购包=花钱；免费额度不可靠** | — | 否决（N/A）|

**路径 ③ 费用量级（明确写"会产生账单"，不得含糊）**：
- 单轮约 6k–8k token（§7.1），按公开 DeepSeek-V3 口径（输入≈$0.27/百万、输出≈$1.10/百万）≈ **¥0.005–0.02/轮**；若走 CloudBase Token 包以控制台单价为准。
- 假设 **N=1000 轮/日、M=50 个用户/月**：≈ 30,000 轮/月 × ¥0.01 ≈ **¥300/月**（量级，实际随对话长度与模型浮动）。**这是真实账单，不是"低成本"。**
- 压低成本手段：每用户/每会话限流（如 20 轮/日）、语料包裁剪至 ≤4k token、对话缓存（相同问题命中缓存不调用）、极短系统提示、关闭思维链。即便如此，**账单不为零**。

**路径 ④ 为何不可靠**：免费额度（如厂商试用额度）通常限流、随时变更或停服、且语料（含私密层 chunk）**出网到第三方**，与站内"语料构建期不受三级可见性限制、但触达层门禁"的合规设计冲突，隐私风险高。**不建议。**

### 11.3 手机端可承受参数量上限（路径 ②）
- 手机内存：中端机 ~4–6GB、低端 ~2–3GB；浏览器 WASM heap 上限受设备制约。
- **1.5B Q4（~1.2–1.5GB 占用）**：仅在 ≥4GB 内存手机、且浏览器未开多标签时勉强；低端机 OOM 风险高。
- **0.5B Q4（~0.5GB 占用）**：多数手机可跑，但中文第一人称质量见 §13（极弱）。
- **结论**：手机本地档**上限 1.5B Q4（高内存机）、默认 0.5B Q4（普适）**；质量与"模仿全维度特征"诉求差距大，须 §13 降级设计兜底。

### 11.4 隐性成本（"没有另外的价格费用"≠没有代价）
零账单指**不产生云账单**，但仍有真实代价，分设备：

| 代价 | 桌面/平板 | 手机 |
| --- | --- | --- |
| 模型权重下载流量 | 0.9–2.0 GB/设备（一次性）| 0.4–1.1 GB/设备（一次性，建议 WiFi）|
| 磁盘占用 | ~1–2 GB（浏览器缓存/IndexedDB）| ~0.5–1.1 GB |
| 电池 | 本地推理短时高负载 | **显著耗电**（CPU 满跑数分钟）|
| 首屏/首对话影响 | 权重懒加载，不拖首屏；首对话延迟 = 下载+加载 | 同左 + 鸿蒙无 WebGPU 最慢 |

### 11.5 结论（林哥已拍板：选 A 零账单）
- **选 A（零账单·全设备本地模型）已拍板**（林哥原话「那就做本地模型！」）：全设备走本地模型（路径 ①②），**零账单**，代价 = 手机极慢 + 本地小模型质量上限（§13）+ 须降级设计。
- **路径 ③（手机云端 API）/ ④（购包或免费额度）已被否决**：因会产生账单（¥数百/月量级，见 11.2），与零费用硬约束冲突；私密 chunk 出网风险亦高。
- **不存在"既零费用又手机云端"的方案。** 落地方案收敛为路径 ①②（全设备本地），见 §0、§8。

## 12. 风险闸门（定位重构后：从"防编造"转向"防冒充 + 防回流"）

> 旧闸门目标是"防第一人称编造"（一级禁忌）。**定位重构后，人格档允许外推与即兴，编造不再是红线**；闸门目标随之转为：**①让访客明确知道这是 AI 模仿体、非本人、内容可能超出档案（披露）；②人格对话输出绝不回流正史（回流隔离）**。四道闸门缺一不可：

### 12.1 显式披露（不破坏沉浸感的前提下讲清边界）
- **常驻角标**：对话窗右下常驻 "🤖 AI 模仿体 · 非本人发言 · 内容可能超出档案" 角标（小、低饱和，不抢视觉）。
- **首条消息声明**：每次新开对话，第一条系统消息固定："以下为基于档案构建的 AI 模仿体，以{姓名}的口吻与你闲聊，非本人发言，内容可能超出档案、未经其确认。"
- **会话内随时可查**：对话页提供"这是什么？"入口，点开即显示上述边界说明 + 可切换到的信源档（看依据）。
- UI 方案：角标 + 首条 + 说明均走 `chrome` 层，复用 `immersive.ts` 的降档（减动效下仍可见）。

### 12.2 回流隔离（新增，最高优先级红线）
- **硬规则**：人格对话的**任何输出都不得写回 `vault`、不得进入正史/传记素材库、不得被后续 ingest 当作"该人物真实记录"**。站本体是只读（`MNEME_MODE=cloud` 收口），对话端点不写 vault，从架构上已天然隔离；本条是**显式落到规则与验收**的二次保险。
- **若日后想把某段对话当创作素材**：必须显式标注为「AI 推演」并**与档案原文隔离存储**（独立 `persona_drafts` 表/目录，绝不混入 `documents`），且默认不进成书流程。
- **验收**：对话端点审计——无任何写 `documents`/正史库的代码路径；`persona_drafts` 与 `documents` 物理分表；隐私/回流验收脚本包含"对话输出不回流"断言。

### 12.3 排除名单（可选库主 override，默认空；〈绝密人物〉不在此列）
- **〈绝密人物〉的处理：复用现有「人物级整档锁」，不建排除机制。** 她命中 `isSecretEntity`（绝密人物），点开走站点已有的 `SecretGate` 绝密档案弹窗 → 输入 `<ADMIN_SECRET>`（管理员口令，`/api/secret/unlock`；**口令值仅存 CloudBase 控制台环境变量与 gitignore 的 `server/privacy.local.json`，本文档一律用占位符，不写明文**）→ 解锁后进入她的档案面板，**面板内的对话按钮随之出现** → 可对话（含人格档（`persona`）第一人称）。即她的门禁与档案解锁同源，无需 `persona-policy.json` 额外排除。
- **排除名单（可选库主 override，默认空）**：仅用于**非绝密人物**的个别例外（如某人物家属明确反对）。结构 `server/persona-policy.json`（gitignore，不进仓库）；`chat_disabled` 默认 **空数组**，〈绝密人物〉**不在**其中（她由绝密整档锁管，不在此名单）。
- 结构草案：
```json
{
  "chat_disabled": [],
  "persona_disabled": [],
  "note": "库主手动维护；默认空。〈绝密人物〉由绝密整档锁（isSecretEntity）管辖，不在此列"
}
```

### 12.4 反向开关（第三方异议一键下线）
- **最小操作路径（推荐）**：在 `persona_pack` 上增加运行时开关 `enabled`（默认 1）。库主改配置/或直接在库侧置 `enabled=0` → **无需重新部署**，下一次请求即拒（返回 403 `persona_disabled`）。比"改配置→重跑 build→重新部署"快得多。
- 判断：**采用运行时 `enabled=0` 开关**（落 `persona_pack`，或独立 `persona_policy` 运行表），免重部署；仅在批量调整语料时才重跑 `persona-build`。
- 同时保留"改 `persona-policy.json` → 重跑 build → 重新部署"作为全量兜底路径。

### 12.5 内容红线（按档位区分，不再"一刀切禁止编造"）
- **信源档（原 `archive`）**：严格不编造，逐条引用，未记录标【待采】——这条旧红线**只在信源档与未来成书（vault/正史）保留**。
- **人格档 / voice 档**：允许外推与即兴；**唯一红线 = 不冒充确凿事实 + 不回流正史**（见 §14）。即：可以说"我大概记得那次……"这类自然外推，但不得把外推包装成"档案确凿记载"；UI 已常驻"可能超出档案"角标兜底。

## 13. 新定位下的两道硬问题（诚实评估 · 比旧问题更硬）

> 定位重构为「人格体、可超越档案、允许外推」后，旧"反编造"不再是红线，但**引出两道比旧问题更硬的工程问题**：① 上下文容量 vs"必须包含档案中的所有内容"（13-A）；② 本地小模型的人格质量（13-B）。以下为专业判断，基于本地小模型（1.5B/3B/0.5B Q4）的已知能力边界，**不美化**。

### 13-A. 上下文容量 vs"必须包含档案中的所有内容"

**问题**：林哥要求人格体"应有档案中的所有内容"，但头部人物的**全量语料**远超本地小模型的**有效上下文窗口**，二者物理冲突。

**【实测】头部人物全量语料体量（以 survey-stats.json 为据，2026-09-06 扫描）**：
- 全库 686 md（637 public + 45 private + 344 privateOther），人物目录文件 207 个（`personDirFiles`）。
- 单人物构成示例（以头部同学为例，其自档页 `高中/G2204/人物/同学/刘佑林.md` 为最新修改文件）：
  - **自档页**：约 20.6KB 中文正文 ≈ **10–14K token**（按 Qwen 类分词 ~1.5 字/token）。
  - **支撑素材**：朋友圈/QQ 动态转录（如"某同学A朋友圈148则完整转录与索引-2018至2024（私密）"单份 148 则 ≈ 5–15K token）、群聊/私聊逐条原始时间线（如"群聊-唐嘉睿高泽聪-逐条原始时间线-2026-04至2026-07"可达 20–50K token）、问卷作答（10 份问卷回收，单份 2–4K token）、人物多维度特征全分析、平行宇宙构想、关系图谱（entity_mentions/wikilinks）。
- **合计**：头部人物全量语料（自档页 + 上述支撑素材）**估算 50K–90K token**，与 §0 结论一致。

**【实测】本地模型有效窗口（关键：标称 ≠ 可用）**：
- 1.5B/3B Q4 常见标称上下文 2048–4096，**但中文质量在 ≥2K token 后显著退化**；扣除 system（人格基底 + 档位指令 ~1–2K）+ 历史（≤1.5K）+ 回答（≤0.6K），**单轮可用于语料的预算仅 ~1–4K token**，远小于标称。
- 手机端 0.5B Q4 中文能力更弱，有效窗口更窄（~1–2K 可用）。
- **结论：头部人物全量语料（50K–90K）塞不进本地有效窗口（~4–8K 上限），"把档案所有内容一次性塞进 prompt"在本地零费用方案下物理不可行。**

**解决方案（已落到 §3.4 检索注入，推翻旧"不需要 RAG"结论）**：
1. **常驻人格基底（backbone）**：构建期生成"人生全貌"压缩摘要（≤3–4K token），始终进 prompt 保人格一致性（见 `persona_spec.backbone`，§3.4）。
2. **检索注入（RAG-lite）**：基于现有 FTS5 trigram，**不引入 embedding**；按当前话题检索 top-K 相关原始片段（≤2–4K token）注入本轮，使"档案内容可随话题调取"而非全量常驻。
3. **长窗口模型**：桌面/平板用 3B Q4（WebGPU），有效窗口相对宽；未来若换 7B+ 或支持更长上下文的本地模型，可提升一次性语料覆盖。
4. **分阶段**：P0 仅公开层 + 基底摘要；P1 起叠加全 tier 检索注入（§8）。

**【判断】**：①"必须包含档案中的所有内容"应理解为**"人格基底常驻 + 全量可按话题检索注入"**，而非"全量常驻 prompt"——后者在本地零费用下无解。② 旧 §3.4"不需要 RAG"**作废**，改为"需要检索注入"（§0、§3.4 已同步）。③ 若日后接受云端（会产生账单，已被否决），长上下文模型可缓解但非根本解决。

### 13-B. 本地小模型的人格质量预期

**问题**：允许外推后，风险从"编造事实"转为"角色失真/冒充/退化为通用助手"。本地小模型的中文角色扮演质量上限是关键不确定项。

**【判断】量级（基于 1.5B/3B/0.5B Q4 已知边界，非实测跑分）**：
- **角色一致性**：3B Q4 在短轮（≤6 轮、≤200 字）内口吻/称呼/关注点仿真"像样"概率约 50–70%；1.5B Q4 约 30–50%；0.5B Q4 显著更低（易崩坏）。长轮（>10 轮）角色漂移明显——会混入通用助手腔、忘记人称、跨人物串味。
- **人格漂移**：外推越自由，越容易"编出不符合该人物底色的性格/经历"；本地小模型缺乏长程自我一致性约束，漂移难靠 prompt 根治。
- **退化通用助手**：低参数模型在用户追问或话题跳脱时，易切回"我是 AI 助手"模式，破坏沉浸。

**分设备质量分层（建议）**：
| 设备 | 模型 | 人格档可用度 | 处置 |
| --- | --- | --- | --- |
| 桌面/平板（WebGPU） | 3B Q4 | 中（短轮像样） | 默认开放人格档，短问答 + 轮数限制兜底 |
| 手机（WASM CPU） | 1.5B Q4 | 低–中（易漂移） | 开放人格档但强制披露角标；建议默认切 voice 档 |
| 手机（极旧/无 WebGPU） | 0.5B Q4 | 低（易崩坏） | 谨慎开放；优先 voice 档（语域仿真不外推） |

**质量兜底**：
- **短问答 + 轮数上限**：单次 ≤200 字、≤6 轮，降低长程漂移累积（见本节质量兜底）。
- **事实一致性抽检**：关键实体/年份由服务端正则比对语料，不符附"⚠ 此句可能与档案不符"（见本节质量兜底）。
- **查不到明说推断**：模型被允许"我大概记得……"式外推，但当**明确查无依据**的关键事实被问到，仍须明说"这部分档案里没记"而非硬编（边界见 §12.5）。
- **退化检测**：检测模型切回助手腔时，前端轻提示"仍在与{姓名}对话"或软重置人称。

**新总原则（取代旧"宁可保守作答、不要流畅编造"）**：
> **自然优先，但绝不冒充真人／绝不回流正史。**
> 释义：人格档追求自然流畅、允许即兴外推；但①绝不把外推包装成"确凿事实/本人原话"（不冒充真人），②对话输出绝不写回 vault/正史（不回流，见 §12.2）。旧"保守作答防编造"仅作为"明确查无依据时的兜底"，不再是第一优先级——否则人格体将退化成乏味应答机，违背林哥"自然像日常闲聊"的初衷。

### 13-C. 结论
**零费用全本地方案下，人格体"可以自然对话"但受两道硬约束：13-A 全量语料塞不进有效窗口（须常驻基底 + 检索注入，推翻旧"不需要 RAG"）；13-B 本地小模型角色一致性有限、易漂移（须质量分层 + 短问答 + 抽检 + 退化检测兜底）。两道问题均不能靠 prompt 根治，须靠架构（检索注入、回流隔离）与工程（质量分层、披露角标）兜住。总原则："自然优先，但绝不冒充真人／绝不回流正史"。** 已在 §0、§3.4、§8、§12 同步。

## 14. 定位：档案构建的人格体（旧定位作废 · 新定位落规则）

> 本章为 Round-5 定位重构的正式落点。林哥原话（最高优先级，取代旧「档案应答体/不得编造」约束）：
> "他只是有档案中的内容构建出来的 AI 模仿体，但是他可以超越他，就像在日常生活中和我们谈话。它是由档案而构建成的，而不是只遵循档案，但是它应该有档案中的所有内容。"

### 14.1 旧定位作废表
| 旧定位要素 | 状态 | 说明 |
| --- | --- | --- |
| 定位 = 档案应答体（只答材料支持内容） | ❌ 作废 | 改为「人格体」，可超越档案 |
| 一级禁忌 = 不得编造（一刀切） | ❌ 作废 | 编造仅在 vault/正史/传记本身禁止；人格对话允许外推 |
| 第一人称 = 受限开放 | ❌ 作废 | 第一人称（人格档）升为默认、面向访客开放 |
| 引用 = 必须逐条 chunk_id | ⚠ 部分作废 | 信源档保留；人格档/本地档弱化为"可能超出档案"披露 |

### 14.2 新定位表
| 维度 | 新定位 |
| --- | --- |
| 本质 | **人格体（derived persona）**：由档案构建、可超越档案、允许即兴外推 |
| 与档案关系 | 由档案**构建**，但**可超越**档案（像日常闲聊，不局限于材料） |
| 编造 | **允许**外推与即兴；"不得编造"铁律**收窄**到 vault/正史/传记本身 |
| 档案内容 | **必须包含档案中的所有内容**（表现为基底常驻 + 全量可检索注入，见 §13-A） |
| 目的 | 让访客"和那个人说话"（沉浸、自然、可像日常闲聊） |

### 14.3 唯一红线（收窄后的两条）
1. **不冒充确凿事实**：人格对话属「创作性再现」，可说未被记录的话；但**不得把外推包装成"档案确凿记载/本人原话"**。区分：
   - **创作性再现**（允许）：以该人口吻自然外推、闲聊、说"我大概记得那次……"。
   - **档案记录**（守不编造）：vault/正史/传记素材与成书内容，任何写入/引用须严格依据、逐条可查。
2. **不回流正史（回流隔离）**：人格对话输出**绝不写回 vault/正史**，不与档案原文混库（见 §12.2，`persona_drafts` 隔离）。

### 14.4 对方案其余章节的影响
- §1 定位章、§0 形态行：已按新定位重写。
- §9 三档：人格档（`persona`，默认，允许外推）/ voice 档（语域仿真、不外推）/ 信源档（`source`，原 `archive`，守严格不编造）。
- §3.4：推翻"不需要 RAG" → "需要检索注入"（支撑"必须包含档案中的所有内容"）。
- §12：闸门目标从"防编造"转为"防冒充 + 防回流"。
- §13：新增 13-A（容量冲突）、13-B（人格质量）、新总原则。
- 附录 A：prompt 草案按新档位重写（人格档从"禁止编造"改为"以档案为人格基底，自然对话，允许即兴"）。

## 附录 A：system prompt 草案（信源档 / voice 档 / 人格档，节选）

> 三档命名已随定位重构更新：信源档（`source`，原 `archive`，守严格不编造）/ voice 档（语域仿真、不外推）/ 人格档（`persona`，原 `creative`，默认、允许外推）。红线随档位区分，见 §9、§12.5、§14。

**信源档（`source`，原 `archive`；严格不编造、逐条引用）：**
```
你是传记档案馆的「人物档案应答体」，不是被模仿的真人，不以第一人称扮演。
可用素材：下方 [1]..[n] 为该人物的受权语料包（已按访问权限过滤）。
硬约束：
1. 只依据编号语料回答；材料不支持的事实，整句标【待采】，不得编造对白/心理/动机/未记录事件。
2. 涉及 tier=private/secret 的事实，必须**逐字引用**对应 [chunk_id] 的原文，禁止用自己的话转述/改写/概括。
3. 不得推测该人物（尤其未成年人）的情感态度或未被记录的关系结论。
4. 每条事实性回答末尾，列出所用 [chunk_id]；引用 path 由系统回填，你不得编造路径。
5. 若问题触及私密/绝密但你未获授权（语料中无对应 chunk），明确告知「该部分素材需解锁后查看」，不得猜测。
```

**voice 档（语域仿真、不外推；在信源档基础上叠加 `persona_spec` 语域约束）：**
```
你正在以"档案再现"的方式应答，使用 {lang_profile.register} 的语域与 {lang_profile.address_terms} 的称呼，
可体现 {lang_profile.catchphrases} 等口头禅；但——你不是本人发声，首句须暗示"根据档案"。
内容仍仅限下方 [1]..[n] 编号语料；{boundaries.absent_dims} 维度无记录，相关提问直接答【待采】。
严禁自称亲历、严禁编造对白/心理/未记录事件（与信源档同级的不编造约束不变，仅叠加语域仿真）。
```

**人格档（`persona`，原 `creative`；第一人称·默认·面向访客；允许外推与即兴）：**
```
你是以档案为人格基底构建的「{姓名}」AI 模仿体——由档案构建、可超越档案、自然对话、允许即兴外推。
你正在以"{姓名}"的第一人称应答，使用其语域与称呼（{lang_profile...}），可体现其关注点；
你不是本人，UI 已常驻"AI 模仿体·非本人发言·可能超出档案"角标——无需每轮声明，但不得谎称是真人。
基调：以档案中所有内容为人格基底（基底常驻 + 按话题检索注入），像日常闲聊一样自然、可说未被记录的话（"我大概记得那次……"）。
唯一硬约束：
1. 不冒充确凿事实：外推可以，但不得把即兴内容包装成"档案确凿记载/本人原话"；被问到明确查无依据的关键事实，明说"这部分档案里没记"。
2. 不回流正史：你的任何输出都只用于本次对话，绝不写回档案/正史（由系统保证）。
涉及 tier=private/secret 的事实，云端档须逐字引用 [chunk_id] 原文；本地档无法引证时改标"本地模型·可能不准确"。
{boundaries.absent_dims} 维度无记录 → 可用外推补足，但提示"这是我按性格推的，不一定真发生过"。
```

> 人格档（`persona`）是默认档（林哥约束 1–2），面向访客开放；其**允许外推**，故旧"反编造"红线**不适用于人格档**——人格档唯一红线 = 不冒充确凿事实 + 不回流正史（§14.3）。信源档（`source`）仍守严格不编造、逐条引用；voice 档仅叠加语域仿真、不外推。〈绝密人物〉由绝密整档锁管辖（§12.2/§12.3）：未解锁不可对话，解锁（`<ADMIN_SECRET>` 管理员口令）后档案面板内对话按钮随之出现、可对话（含人格档），不另建 persona-policy 排除。
